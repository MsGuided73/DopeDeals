# Highway 420 — 18-Phase Audit Reconciliation

**Audit date:** 2026-05-05
**Companion to:** the 18-phase JSON audit returned in this session
**Purpose:** Capture every claim from the initial audit that was later corrected, refined, or confirmed during live verification against the running Supabase instance and the actual codebase. Use this alongside the JSON when generating the personalized roadmap — several "HIGH risk" items in the JSON are softer than they read; several "LOW risk" items proved real.

---

## Why this document exists

The initial 18-phase audit was generated by spawning seven parallel `Explore` subagents. Each subagent had a narrow brief (payments, compliance, security, etc.) and returned summaries that were then synthesized into the JSON. That parallelism is fast but introduces a known failure mode: **subagents read excerpts, not whole files, and they cannot tell tracked from untracked git state.** Several findings turned out to be artifacts of that limitation. Other findings stood up under scrutiny but were less severe than first claimed; a few got *worse* after I queried live database state via MCP.

This document is the corrigendum. It is not exhaustive — it covers items where the JSON output diverges from current reality, plus the new findings discovered during verification.

## Section 1 — Findings I retracted

### 1.1 "Committed secrets in `.env`" — FALSE ALARM

**What the audit said (HIGH risk, P0):**
> CRITICAL: .env with production secrets is checked into the repo (rotate immediately) — exposes SUPABASE_SERVICE_ROLE_KEY, ZOHO_*, KAJAPAY_SOURCE_KEY, SHIPSTATION_API_KEY, OPENAI_API_KEY, GEMINI_API_KEY, AIRTABLE_PERSONAL_ACCESS_TOKEN.

**What's actually true:**
- `.gitignore:55` ignores `.env`
- `git ls-files .env` → not tracked
- `git log --all -- .env` → no history of the file ever being committed

The subagent that produced this finding saw `.env` on the local filesystem and assumed committed status. Subagents cannot reliably check git tracking status.

**Implication for the roadmap:** Drop "rotate all secrets immediately / scrub git history." Secrets hygiene is fine. Standard rotation hygiene (e.g. when an admin leaves, after any actual leak) still applies.

**JSON entry to ignore:** `phases[].phase = "Auth & Security" → gaps[0]` and `top_3_priorities[0]`'s "rotate every secret in the committed .env" clause.

### 1.2 "Age gate is bypassable" — TECHNICALLY TRUE, MISCHARACTERIZED

**What the audit said (HIGH risk):**
> Age gate is client-side localStorage only and not enforced in /api/checkout — bypassable via DevTools.

**What's actually true:**
- The age gate **is required before checkout** in normal flow. [app/checkout/shipping/page.tsx:158-161](../app/checkout/shipping/page.tsx#L158-L161) has a mount-level redirect to `/age-verification` if `!isAgeVerified`, plus a click-time guard at line 142-147 before review.
- Server-side enforcement at `/api/checkout` is intentionally absent — [app/api/checkout/route.ts:76-80](../app/api/checkout/route.ts#L76-L80) explicitly comments that the elevated frontend gate is treated as the formal compliance mechanism in the current rollout phase.
- Bypass requires deliberate localStorage manipulation in DevTools by an adult who is *trying* to bypass age verification of a site that will sell them age-restricted product anyway.

**Severity:** Defense-in-depth gap, not an "open door." A determined bad actor can bypass; a normal user cannot. Worth fixing for compliance defensibility, but not the same risk class as a missing age gate.

**Recommendation downgrade:** MEDIUM, not HIGH. Server-side check at `/api/checkout` should look at `auth.users.user_metadata.age_verified` for logged-in users and reject if missing/false. For guest checkout, the LocalStorage flag remains the only signal — that's the actual gap.

### 1.3 "Compliance check missing / heuristic-only" — STRUCTURALLY OK, DATA INCOMPLETE

**What the audit said:**
> Compliance enforcement is partial. THCA detection by name/category, not SKU or cannabinoid profile. Amanita-Louisiana block is MISSING entirely.

**What's actually true (verified live):**
- The compliance check at `/api/checkout` **is in effect and fail-closed**. If the check throws, the order is rejected with HTTP 503, not allowed through. See [app/api/checkout/route.ts:182-190](../app/api/checkout/route.ts#L182-L190).
- The flow: shipping ZIP → `us_zipcodes` lookup → state → `compliance_rules` query → `product_compliance` mapping → 403 with `restrictedProductIds` if any product blocks.
- The THCA name/category heuristic is a *fallback* layered on top of the rule-table check, not the primary mechanism.
- "Amanita-Louisiana block is missing" was true in the rules table, but **the user does not currently sell Amanita products** ("Coming Soon"). It's a launch-blocker for a category that isn't live, not a current exposure. Will need a `compliance_rules` row when amanita products launch — the category string must match how products are tagged.
- Live `compliance_rules.restricted_states` for THCA was `[CA, ID, UT]` only — incomplete vs. the stated 8-state policy `[CA, HI, ID, MN, OR, RI, UT, VT]`. **This is now fixed** (migration `thca_restricted_states_full_eight` applied 2026-05-05).

**Severity:** The data was the gap, not the code. After the THCA migration the immediate exposure is closed.

## Section 2 — Findings that got worse on inspection

### 2.1 RLS `USING (true)` policies — granted to `public`, not `authenticated`

**What the audit said:**
> RLS policies using `USING (true)` on page_builder tables (20250120_page_builder_schema.sql:219-224)

That migration text says `TO authenticated`. The **live database** has those same policies bound to the `public` role, which in Supabase corresponds to the anon key shipped to every browser. So:

| Table | Live policy (before fix) | Effective access |
|---|---|---|
| `page_templates` | `ALL TO public USING (true)` | Any browser: full CRUD |
| `user_pages` | `ALL TO public USING (true)` | Any browser: full CRUD |
| `component_library` | `ALL TO public USING (true)` | Any browser: full CRUD |
| `design_themes` | `ALL TO public USING (true)` | Any browser: full CRUD |
| `page_analytics` | `ALL TO public USING (true)` | Any browser: full CRUD |
| `media_assets` | `ALL TO public USING (true)` | Any browser: full CRUD |

All six tables happened to be empty (verified via `SELECT COUNT(*)`), so there was no data leak — but a malicious actor could have written arbitrary content into the page-builder system at any time.

**Fix shipped:** Migration `tighten_page_builder_rls_and_user_behavior` applied 2026-05-05. Replaced with `ALL TO authenticated USING (((auth.jwt() -> 'app_metadata') ->> 'role') = 'admin')`. Public-read on `user_pages` for `status='published'` rows is preserved.

### 2.2 `user_behavior` — RLS was DISABLED, not weak

**What the audit said:** Not flagged.

**What was true:** `user_behavior` had `relrowsecurity = false`. Anyone with the anon key could read/write the entire user behavior tracking table.

**Fix shipped:** `ALTER TABLE user_behavior ENABLE ROW LEVEL SECURITY` applied in the same migration. Service-role only by default; layer per-user SELECT later if the app needs it.

---

### 2.3 `us_zipcodes` and `product_compliance` — RLS enabled with zero policies

**What the audit said:** Not flagged for either.

**What was true:**
- Both tables had RLS enabled but no policies defined → effectively service-role-only.
- The eligibility route at [app/api/eligibility/route.ts:21-22](../app/api/eligibility/route.ts#L21-L22) constructs its Supabase client with `SUPABASE_SERVICE_ROLE_KEY || NEXT_PUBLIC_SUPABASE_ANON_KEY`. If service-role isn't injected (CI placeholder, misconfigured env, edge runtime constraint), the anon fallback runs — and against tables with zero policies, every query returns empty.
- Empty result for `us_zipcodes` → "ZIP not found in compliance database" → eligibility route returns "no restrictions." **Fail-open under misconfiguration.**
- Empty result for `product_compliance` → checkout sees zero blocked products → potentially ships restricted product to a banned state.

**Fix shipped (partial):** Public-read policy added to `us_zipcodes` (zip data is non-sensitive reference data). `product_compliance` left service-role-only — the right pattern is to enforce server-side that the client always uses service role; left as a follow-up.

---

### 2.4 `requireAdmin()` has a dead-code fallback

**What the audit said:** Not flagged.

**What was true:** [app/lib/requireAuth.ts:27-32](../app/lib/requireAuth.ts#L27-L32) tries to read `role` from `public.users` as a fallback. The `public.users` table **has no `role` column** (verified via `information_schema.columns`). Every call to that fallback throws → caught at line 37-39 → returns `UserRole.USER`.

**Effective behavior:** Only `app_metadata.role` and `user_metadata.role` actually grant admin. The profile-table path is decoration. All four current admins are caught by the JWT path so this hasn't bitten anyone, but the function is lying about its own logic.

**Status:** Not yet fixed. Either add the column or delete the dead branch.

## Section 3 — Findings that stood up unchanged

### 3.1 Service-role-before-auth in admin endpoints — STILL HIGH RISK

20+ admin endpoints construct a service-role client at module top-level, before `requireAdmin()` runs. Examples:
- [app/api/admin/dashboard/stats/route.ts:4-7](../app/api/admin/dashboard/stats/route.ts#L4-L7)
- audit-log, blog, carousel/setup, orders/[orderId], etc.

If any of those endpoints is reachable without `requireAdmin()` running first (e.g. a future refactor that forgets the gate), the request gets full RLS bypass. The pattern is the bug, not any single instance.

**Recommendation:** Land a single `getAdminSupabase()` helper that gates the client construction inside the auth check, and migrate all admin routes to use it. Pre-existing JSON priority #1 (after retracting the secrets clause) — **stands.**

### 3.4 ShipStation v2 client wired correctly; v1-era env example was misleading

The audit didn't address this directly. During the conversation we verified:
- Client targets `https://api.shipstation.com/v2` ([client.ts:112](../lib/services/shipstation/client.ts#L112)).
- v2 only requires `SHIPSTATION_API_KEY` (single header `API-Key`); the `SHIPSTATION_API_SECRET` in `.env.example` is a v1-era artifact.
- Hardcoded fallback ZIP `78701` (Austin) was wrong. The `.env` had `75001` (Addison, TX), but that turned out to also be wrong on later confirmation from Dana — the real BMB Wholesale warehouse is **`03079` (Salem, NH)**, consistent with the "East Coast Warehouse" references in `B2C_SYNC_STRATEGY.md` and `ZOHO_INTEGRATION_STEP_BY_STEP.md`. **Fixes shipped:**

- `.env.example` updated with `SHIPSTATION_FROM_POSTAL_CODE` and `SHIPSTATION_WEBHOOK_SECRET` slots.

**Still open:**
- Webhook in [app/api/shipstation/webhook/route.ts](../app/api/shipstation/webhook/route.ts) accepts unsigned POSTs. v2 supports `X-Shipstation-Hmac-Sha256` — needs to be verified.
- The "DO NOT change mock elements" guard in [lib/services/shipstation/service.ts:60-65](../lib/services/shipstation/service.ts#L60-L65) needs to be removed now that credentials are present.

## Section 7 — Methodology lessons for future audits

Things that would make the next 18-phase audit more accurate without slowing it down:

1. **Verify gitignore status before reporting "committed secrets."** A subagent that runs `git check-ignore` and `git ls-files` before flagging a file as exposed eliminates ~80% of false-positive secret findings.
2. **Query the live database** before reporting on RLS policies. Migration files describe intent; `pg_policies` describes reality. The two diverged on six tables here.
3. **Don't trust audit subagents on git or filesystem boolean facts.** They read excerpts. Tracked-vs-untracked, file-exists-vs-committed, env-set-vs-default — all need a separate verification pass.
4. **Severity should split "exists / works correctly" from "is enforced at every layer."** The age gate findings flipped between "missing" and "present" depending on which layer the subagent looked at. A clearer rubric would distinguish "no enforcement anywhere" (HIGH) from "enforced in UI only" (MEDIUM).
5. **Cross-reference data with code.** The "Amanita-LA missing" finding was a code observation; the user-context "we don't sell amanita yet" reframed it from a current gap to a launch-time prep item. Audits without business context overweight code-only findings.
